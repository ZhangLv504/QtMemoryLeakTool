# 1.为什么要加一个(void)p;

```c++
auto p = new std::uint64_t[4];
(void)p;
```

在这段代码中，加上 `(void)p;` 的唯一目的是**消除编译器的“未使用变量”（unused variable）警告**。

具体原因如下：

**1. 编译器的安全检查** 在 C/C++ 开发中，如果我们声明了一个变量 `p`，但在后续代码中从未读取或使用过它，编译器（尤其是开启了 `-Wall` 或更高警告级别的 GCC/Clang，或 MSVC 的 `/W4` 时）就会抛出一个警告，比如： `warning: unused variable 'p' [-Wunused-variable]`

**2. 为什么会有这种测试代码** 结合你前面发出的测试程序，这里的核心意图是**故意制造一次内存泄漏**，用来验证内存跟踪器（MemTracker）是否能检测到它。所以，代码只需负责分配内存（`new`），**根本不需要去使用这块内存**。

**3. `(void)p;` 的作用机制** 如果某些工程开启了“将警告视为错误”（如 `-Werror` 或 `/WX`），上述的未使用变量警告会导致编译直接失败。 写下 `(void)p;` 实际上是做了一次表达式求值（把 `p` 强制转换为 `void` 类型），然后丢弃结果。 这样就巧妙地骗过了编译器，相当于告诉编译器：“你看，我已经‘用’过这个变量了，不要再烦我了。” 这种写法在编译到机器码时会被完全优化掉，**没有任何运行时的性能开销**。

**补充：** 在现代 C++（C++17 及以后）中，更优雅、语义更明确的替代方案是使用 `[[maybe_unused]]` 属性，可以直接写在声明时：

```c++
[[maybe_unused]] auto p = new std::uint64_t[4];
// 不需要再写 (void)p;
```

但在很多老代码或兼容老版本 C++ 的库中，`(void)p;` 依然是最通用且最常见的消除未使用警告的惯用法。

# 2.MemTracker.cpp 为什么能看到 memtrack_core 的头文件（include 路径 ≠ 链接）

```cmake
add_library(memtrack_core STATIC
    MemTracker.cpp
)

target_include_directories(memtrack_core PUBLIC
    "${CMAKE_CURRENT_SOURCE_DIR}"
)
```

这个目标没有 `target_link_libraries(memtrack_core ...)`，`MemTracker.cpp` 仍然能 `#include "MemTracker.h"`，原因有两点。

**1. `PUBLIC` 同时作用于“自己”和“消费者”**

`target_include_directories(... PUBLIC dir)` 等价于 `PRIVATE` + `INTERFACE`：

- `PRIVATE` 部分作用于本目标自己的编译：编译 `MemTracker.cpp` 时，CMake 会把 `/I<...>/memtrack_core`（GCC/Clang 为 `-I`）加进编译命令行，所以能找到同目录的三个头文件。
- `INTERFACE` 部分作用于消费者：`Phase1Demo` 链接了 `memtrack_core`，CMake 就把同一个 include 目录传递给它。所以 `demo/phase1/CMakeLists.txt` 里不用再写一遍 include 路径，`main.cpp` 直接写 `#include "MemTracker.h"` 即可。

如果这里写成 `PRIVATE`，库自己仍可编译，但 `Phase1Demo` 找不到头文件就会编译失败——`PUBLIC` 的意义正在于此。

**2. 链接和 include 是两件独立的事**

- 链接决定“符号从哪里来”：`memtrack::start`、全局 `operator new` 等实现由 `memtrack_core.lib` 提供，靠 `target_link_libraries` 解析。
- include 路径决定“头文件从哪个目录找”，它只是编译命令行上的 `/I` 参数，完全由 `target_include_directories` 决定，不需要也不依赖链接。

**3. 引号形式还有一层兜底**

`MemTracker.cpp` 里写的是 `#include "MemTracker.h"`（双引号）。按标准，编译器会**先搜索包含该文件的当前目录**，再搜索 `/I` 指定目录。因此即使没有那条 `target_include_directories`，同目录的头文件也总找得到；`/I` 真正保证的是“别的目录的源文件也能按文件名包含”，例如 `demo/phase1/main.cpp` 里的 `#include "MemTracker.h"`。
